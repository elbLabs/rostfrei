# Initial aggregate-readiness benchmark results

Measured with the [aggregate benchmark suite](aggregate-loading.md), using the
working tree containing the preceding history-read optimizations. Git base:
`44bba64f2c2ac756f2f06cd436fc6e62b79433ab`; the report records `git_dirty: true`.
These are not measurements of an unmodified published release.

## Aggregate ready for use

The `rehydrate` timer stops when
`CommandExecutor::rehydrate::<InventoryAggregate>()` returns the populated,
usable aggregate—not when event history merely arrives.

| History | Events | Ready median | Ready range, 5 samples | History requests |
| --- | ---: | ---: | ---: | ---: |
| Direct batches | 100 | **61.36 ms** | 26.35–137.14 ms | 102 |
| Direct batches | 1,000 | **419.38 ms** | 368.26–780.59 ms | 1,002 |
| One command transaction per event | 100 | **110.91 ms** | 78.28–165.45 ms | 306 |
| One command transaction per event | 1,000 | **1,699.85 ms** | 1,652.77–2,576.56 ms | 3,017 |

The 1,000-command history was generated by actually executing 1,000 commands and
persisting their event transactions/receipts. It took about **855 seconds to
prepare and load its fixture**; that preparation time is excluded from the sample
measurements.

## How much does apply add?

The suite instruments the history provider inside each full rehydration call.
`after_history_ns` covers the remaining runtime history validation, typed JSON
decoding, aggregate initialization, and event application. A separate apply-only
phase starts with decoded events prepared before its timer.

| History | Events | Runtime work after history, median | Apply-only median |
| --- | ---: | ---: | ---: |
| Direct batches | 100 | 0.146 ms | 0.0067 ms |
| Direct batches | 1,000 | **1.808 ms** | **0.0550 ms** |
| Command transactions | 100 | 0.282 ms | 0.0077 ms |
| Command transactions | 1,000 | **3.571 ms** | **0.0516 ms** |

For this inventory model, history retrieval and transaction validation dominate.
The domain's apply operation is inexpensive. A different domain with costly
apply logic, larger state, or larger payloads can behave differently.

## Other measured phases

| History | Events | History-only median | New executor-command median | Command starting histories |
| --- | ---: | ---: | ---: | ---: |
| Direct batches | 100 | 58.32 ms | 152.19 ms | 100–104 events |
| Direct batches | 1,000 | 485.09 ms | 596.25 ms | 1,000–1,004 events |
| Command transactions | 100 | 119.73 ms | 147.48 ms | 100–104 events |
| Command transactions | 1,000 | 1,775.45 ms | 1,627.90 ms | 1,000–1,004 events |

Every timed executor command had a new operation identity and appended one new
event. These calls include persistence and verification, but not HTTP, command-bus
queueing, durable command-response waiting, or post-commit integrations.

The phases are independent observations on a shared host. A lower full-readiness
median than history-only median, or a lower executor median than readiness
median, reflects changing sample conditions—not negative decoding or free write
cost. Use the paired intervals inside each `rehydrate` sample to understand its
components; do not subtract independent phase medians.

## Configuration and verification

- Rust 1.98.0, optimized Cargo benchmark profile.
- Disposable NATS 2.12.1, one replica, file storage.
- Linux x86-64; 16 available CPUs; benchmark runtime explicitly uses 2 workers.
- Inventory projection over 64 SKU identities in a `BTreeMap`.
- 128-byte note fields; the 1,000-event fixture contains **160,840 bytes of
  domain JSON payload**, before storage envelopes/headers and receipts.
- One read warmup per phase; write warmups use a separate aggregate.
- Sizes 0, 100, 1,000; both history kinds; five samples per phase.
- **120 timed samples** passed state/outcome checks. Post-processing verified
  history-size accounting, zero NATS traffic for apply-only, and exact
  `history_load_ns + after_history_ns == elapsed_ns` for every rehydration sample.
- Four broker-free fixture/report/CLI contract tests passed, including large
  payloads crossing direct-batch byte limits.
- The actual NATS smoke matrix (0 and 3 events) and the full matrix both passed.
- Clippy, formatting, version consistency, and diff checks passed.

No p95 is reported with five samples. These warm, single-client measurements on
a shared development host do not establish production tail latency or cold-cache
behavior.

## Artifacts and reproduction

The complete local report is `/tmp/opencode/rostfrei-aggregate-loading.json`.
The process log is `/tmp/opencode/rostfrei-deep-review-aggregate-loading.log`.
Both are local artifacts; this document preserves the result summary.

```sh
cargo build --locked --release -p rostfrei-benchmarks --bins
target/release/rostfrei-benchmarks aggregate-loading -- \
  --events 0,100,1000 --samples 5 \
  --output /tmp/rostfrei-aggregate-loading.json
```

The suite and all parameters are documented in
[aggregate-loading.md](aggregate-loading.md).
