NATS subjects, explained

One address.
A lot of intention.

A subject is the dot-separated address on a NATS message. Rostfrei gives that address a predictable shape: which application, which traffic scope, what kind of message, and which bounded context owns it.

Let’s follow renting a bicycle through the real bike-rental example.

Examples
01

Routing, storage, and history.

These three concepts work together, but answer different questions.

Where does the message go?

NATS subject

An address attached to a message. Subscribers and JetStream streams use subject filters to select messages.

Where is it retained?

JetStream stream

A broker storage resource that captures matching subjects. A single stream can contain many different subjects.

What happened to this aggregate?

Aggregate stream

The ordered domain-event history of one aggregate identity. The NATS event store maps that history to one opaque aggregate subject.

Why does “bike-rental” appear twice? The example gives its application and its bounded context the same name. The first token scopes the whole application; the later token identifies the context inside it.

Showing Normal traffic: no extra scope token is inserted.

The general business-address shape: <application>[.test].<kind>.<bounded-context>.<name>. Brackets mean the literal .test is optional; they are not part of the subject. Aggregate IDs, correlation IDs, and schema versions belong in the message or storage envelope, not extra business-address tokens.
02

Six subject families to recognize.

Commands ask for a decision. Domain events preserve the private facts. Integration events communicate public facts. The other families carry outcomes, read requests, and quarantined deliveries.

command · durable work

“Please rent this bicycle.”

RentBicycle is routed to a command worker. Its payload identifies the fleet and bicycle.

bike-rental.command.bike-rental.rent-bicycle
command-response · durable outcome

“Accepted” or “Rejected.”

The adapter derives an exact response address from the command address, operation ID, and command message ID. The retained result is distinct from a broker publish acknowledgement.

bike-rental.command-response.bike-rental.<response-digest>
domain · authoritative private history

“BicycleRented happened in this fleet.”

The event store appends BicycleRented to the fleet aggregate’s history. The last token is derived from the aggregate type and ID; different event types for that aggregate share this subject.

bike-rental.domain.bike-rental.aggregate.<aggregate-digest>
integration · public contract

“A bicycle rental has started.”

After commit, the example maps the private event to the separately versioned BicycleRentalStarted contract and publishes it through IntegrationEventBus.

bike-rental.integration.bike-rental.bicycle-rental-started
query · Core NATS request/reply

“Is this bicycle available?”

A NATS query adapter uses a query subject without a JetStream query stream. Replies use transport-managed inboxes.

Illustrative address: the example defines a domain-level availability query; its current runtime does not mount a NATS query responder for it.

bike-rental.query.bike-rental.bicycle-availability
quarantine · delivery triage

“This delivery needs inspection.”

A quarantined delivery keeps the source kind, context, and name in its address. For example, a quarantined rental command would use the subject below. A normal business rejection uses a command response.

bike-rental.quarantine.command.bike-rental.rent-bicycle

Angle-bracketed digests are explanatory placeholders, not literal subjects or NATS wildcards. Rostfrei derives the real opaque values.

03

Follow one rental.

This is a source-based walkthrough of the accepted path in examples/bike-rental. It assumes the demo fixture’s serviceable bike-42 is still available in city-fleet.

Rent bike-42 from city-fleet. Command: RentBicycle · Schema version: 2 · Aggregate: RentalFleetAggregate

  1. Publish the command to the use-case address.

    CommandBus derives the address from the bound context and the command’s local ID, rent-bicycle. The durable command stream captures it.

    bike-rental.command.bike-rental.rent-bicycle 
    {
  "fleet_id": "city-fleet",
  "bicycle_id": "bike-42"
}

    This is the business payload. The bus supplies the surrounding message envelope and execution identities. Neither city-fleet, bike-42, nor schema version 2 is appended to the command subject.

  2. Load the fleet and make the domain decision.

    The NATS worker hands the command to the registered processor and RentBicycleHandler. The handler loads RentalFleetAggregate for city-fleet through CommandExecution. The aggregate is reconstructed from its history, and the rental behavior checks eligibility.

  3. Commit the private fact to the fleet’s history.

    On success, BicycleRented is appended through NatsEventStore, with the expected aggregate stream version. The fleet is the aggregate; the bicycle is an entity inside it.

    bike-rental.domain.bike-rental.aggregate.<aggregate-digest>

    This subject also holds that fleet’s added, returned, retired, and transferred domain events. Event type is stored in the event envelope, not in the subject.

  4. Report the outcome and publish the public fact.

    Two separate responsibilities follow the successful commit:

    Back to the caller

    Accepted response

    The command worker publishes a durable outcome on the derived response address, so the caller can retrieve it.

    bike-rental.command-response.bike-rental.<response-digest>
    Out to consumers

    BicycleRentalStarted

    A durable domain-event consumer maps the committed event to this public schema-v1 event. A separate durable integration-event consumer handles and logs it.

    bike-rental.integration.bike-rental.bicycle-rental-started

    The response and integration-event publication are separate post-commit paths. Their relative arrival order is not a contract; an accepted response does not mean all downstream consumers have finished.

What if the bicycle cannot be rented?

The fixture also includes maintenance-required bike-99. A business rejection returns a rejected command response and appends no rental domain events. There is consequently no BicycleRentalStarted from that rejected attempt. The command subject stays the same; the outcome changes.

What if a command touches two fleets?

TransferBicycle uses the transfer-bicycle command name with source and destination fleet IDs in its payload. It records BicycleTransferredOut and BicycleTransferredIn on two different aggregate subjects. Both commits belong to one atomic event transaction in the same bounded-context event store.

bike-rental.command.bike-rental.transfer-bicycle

Subjects route. Streams retain.

Rostfrei derives four messaging streams per application and traffic scope, plus one authoritative domain-event stream per bounded context and scope. Stream names use uppercase letters and underscores; subjects keep lowercase kebab-case tokens.

A stream name does not namespace subjects. Separate Normal and Test stream names alone are insufficient; their subject filters must also be disjoint. Provisioning is explicit: operators create the topology, then runtimes connect and verify it. The local example explicitly provisions its demo resources during startup.

How wildcards work

*
Matches exactly one token. bike-rental.command.bike-rental.* selects every command name in this context.
>
Matches one or more trailing tokens and must be last. bike-rental.command.> selects Normal commands across the application’s contexts.

Wildcards belong in subscriptions and storage filters. A published business message has one concrete, validated address.

Private storage has internal subjects too

The domain-event stream also contains operation-scoped transaction receipts and read guards under transaction.<operation-digest> and transaction.<operation-digest>.guard.<ordinal>.

Domain-event consumers select aggregate.*, so these internal records are excluded. A JetStream stream sequence is therefore different from an aggregate’s own event version.

05

Same application. Isolated Test traffic.

Select TrafficScope::Test when constructing the context. Rostfrei inserts .test immediately after the application token and derives separate streams and consumer identities. These two cards always show both scopes for comparison.

TrafficScope::Normal

No scope token

bike-rental.command.bike-rental.rent-bicycle BIKE_RENTAL_COMMANDS BIKE_RENTAL__BIKE_RENTAL_DOMAIN_EVENTS
TrafficScope::Test

Insert the reserved “test” token

bike-rental.test.command.bike-rental.rent-bicycle BIKE_RENTAL__TEST_COMMANDS BIKE_RENTAL__TEST__BIKE_RENTAL_DOMAIN_EVENTS
  • The application identity remains bike-rental in both scopes. Normal is not a literal .normal or .prod token.
  • The example’s Test reset recreates only its isolated Test resources. Normal history persists.
  • Scoped adapters validate application and traffic scope, so a Normal component rejects a Test address and vice versa.
  • The stream-name marker __TEST distinguishes Test resources from the Normal resources of a separately named application such as bike-rental-test.
Read broad filters literally. bike-rental.> includes both scopes. bike-rental.command.> matches only Normal commands; bike-rental.test.command.> matches only Test commands. This distinction matters for subscriptions and NATS permissions alike.
06

Derive addresses from a context.

Application code supplies the business names. The typed messaging API handles validation and the namespace. This small example uses the same derivation APIs as the bike-rental configuration.

use rostfrei_messaging_core::ApplicationName;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let application = ApplicationName::new("bike-rental")?;

    let normal = application.bounded_context("bike-rental")?;
    let test = application.test_bounded_context("bike-rental")?;

    let command = normal.command_address("rent-bicycle")?;
    let test_command = test.command_address("rent-bicycle")?;
    let public_event = normal
        .integration_event_address("bicycle-rental-started")?;

    assert_eq!(command.as_str(),
        "bike-rental.command.bike-rental.rent-bicycle");
    assert_eq!(test_command.as_str(),
        "bike-rental.test.command.bike-rental.rent-bicycle");
    assert_eq!(public_event.as_str(),
        "bike-rental.integration.bike-rental.bicycle-rental-started");

    Ok(())
}

Names are validated tokens

Application, context, and business-name tokens use lowercase ASCII letters, digits, and single hyphens. Tokens are nonempty, cannot start or end with a hyphen, and cannot contain repeated hyphens, dots, spaces, or wildcards. Each token is limited to 64 bytes; a business address to 256 bytes.

A durable name is a different identifier

The rental command’s Normal durable is bike-rental--bike-rental--rent-bicycle--v2. Test inserts --test after the application. The version belongs to the consumer identity and message schema; the subject still ends in rent-bicycle.
