# Introduction

Rostfrei is a Rust framework for event-sourced applications. Business rules stay in ordinary Rust; the framework connects them to durable command execution, messaging, read models, and runtime inspection.

Applications depend on `rostfrei` and enable the adapters they need. The bike-rental example combines NATS storage and messaging, HTTP routes, and Tracer with its domain code.

**New here? [Explore with your agent](getting-started.mdx).** Copy a prompt to prepare an isolated demo and inspect a successful rental and a rejection through real Tracer evidence.

## How the pieces fit

| Piece | Role in the application |
| --- | --- |
| **Domain code** | Actions, policies, and event application in ordinary Rust, with [declarations](domain-macros/index.mdx) for names and ownership metadata. |
| **Command runtime** | Loads aggregates, checks stream versions, and atomically commits accepted events and completed outcomes. Exact retries return the recorded decision. |
| **Messaging and HTTP** | Typed buses connect commands, queries, and integration events. [NATS adapters](messaging/subjects.mdx) provide durable storage and delivery; the HTTP adapter exposes explicitly mounted routes. |
| **Read models** | [Saved query views](read-models/index.mdx) maintained by typed event handlers, with persistence, source checkpoints, and concurrency retries. |
| **Testing and inspection** | Tracer exposes command contracts, isolated behavioral tests, and bounded observations. Coding agents use its API; Studio is an optional visual client. |
| **Project tooling** | [Checked directories](project-structure/index.mdx), ownership and implementation validation, and compiled domain metadata. |

See [dependency setup](getting-started.mdx#one-framework-dependency) and the [workspace crates](README.md#workspace-crates) for features and package boundaries.

## Domain code

The framework handles recurring storage and execution mechanics. The application still decides what a rental means, which bicycles are eligible, and whether a return requires inspection. Discussing that model is part of the work.

Declarations and implementations have predictable locations in the source tree. Behavioral tests specify setup, commands, and expected outcomes so changes can be checked against the running application. Humans and coding agents work from the same contracts and evidence.

## The mental model

Imagine a customer renting a bicycle:

1. A **command**, `RentBicycle`, asks the Bike Rental bounded context to make a business decision.
2. Domain behavior checks the fleet and its rental policy. An unavailable bicycle produces a **rejection** and no new domain events.
3. An accepted rental produces a **domain event**, `BicycleRented`. The runtime commits it to the fleet's private history. Replaying that history reconstructs the aggregate's state.
4. After the commit, application code maps the private fact to a separately versioned **integration event**, `BicycleRentalStarted`, for public communication.

A query reads state without changing it. A domain policy evaluates facts without changing state or recording events.

## Why events are the foundation

A fleet's bicycles and their availability are reconstructed from events such as `BicycleAdded`, `BicycleRented`, and `BicycleReturned`. With event sourcing, domain data is derived from those recorded facts. The history is the source of truth.

The same facts can reconstruct an earlier aggregate version, support another view of rental activity, or establish a test fixture. Replay applies recorded events; it does not resubmit the original command or publish another integration event. New views can use what was recorded, but cannot recover facts the application never captured.

Read models serve queries without replaying history on every request. The runtime handles persistence and source checkpoints; the application owns schemas, compatibility mappings, and [projection rebuilds](read-models/ordering.mdx).

Event history and runtime observation answer different questions. The store retains authoritative domain history; [Tracer observations](continuous-observation.md) are partial, retained windows of activity. A message trace alone is not a business-completion verdict.

## From command to decision

The rental command carries fleet and bicycle IDs. Its action evaluates eligibility, then raises `BicycleRented` or returns a rejection. The runtime commits the decision and accepted events after checking the versions it read.

An exact retry returns the recorded outcome. A deliberate new request uses a new operation identity. A timeout means the caller may not know whether the command completed; it is not a business rejection. See the [command runtime](command-runtime.md) for identity, retry, and outcome contracts.

## When Rostfrei fits

Rostfrei is aimed at applications where business rules, consistency boundaries, and the history of change are central to the design. Explicit ownership and inspectable behavior help teams keep agent-assisted development understandable as the codebase grows. The example shows both single-fleet decisions and a bicycle transfer committed atomically across two fleet aggregate streams in one event store.
